## Core Entities

- **Goal** — a shared purpose people join (public, invite-only, or personal)
- **Contract** — your personal time commitment to a goal (e.g. "1 hour/week")
- **Commit** — a logged unit of progress against your contract
- **Instruction** — expert-authored action plan for a goal

## Four Dimensions

Every Commit carries a `dimension_tag`:

| Tag | Meaning |
|-----|---------|
| `faith` | Acting in uncertainty toward a meaningful path |
| `will` | Obligations, contracts, routine |
| `feeling` | Creativity, hobbies, subjective experience |
| `mind` | Analysis, knowledge, cognitive work |

**Hunger-first:** show dimensions in order from least-fed to most-fed.
Daily Compass takes the order from the platform's `dimension_order` (never-fed first); the list below is only the fallback when the platform is unavailable, and the output is then flagged.

faith, will, feeling, mind

## Daily Compass

The Daily Compass is the daily companion projection: *"What do my areas say about today?"*

It's implemented as daily-compass.py script in this skill.

Morning cron behavior for MVP:

- Morning run outputs only `## Logos` checklist candidates.
- The checklist comes from Hermes-generated `AreaContext` output.
- It updates `Compass.md` to keep exactly two top-level sections: `## Logos` and `## Shared Goals`.
- User-owned checkbox items stay in `## Logos`.
- Agent candidate recommendations are written in a managed non-checkbox block inside `## Logos`.
- `## Shared Goals` is fully generated by agent and grouped by `faith`, `will`, `feeling`, `mind`.
- Automatic insertion into `Compass.md` is out of scope for this phase.

## Area File Format

Each file in `references/` defines one area. Filename = area identity.
One file per area — DRY, no duplication across dimensions.

```yaml
# references/example-area.yaml
name: Example Area               # human-readable name
dimensions: [faith, will]        # one or more: faith | will | feeling | mind
skill: skill-name                # hermes skill to call for status, or null
status: active                   # active | TBD
notes: ""                        # human-readable description (for ls references/)
```

Files in `references/` are gitignored. Never commit them. Never reference
specific area names or skill names in this SKILL.md.

Daily Compass full runs include live platform data from
`GET /api/v1/compass/next-steps` when configured. Selected-area debug runs keep
using local `references/*.yaml` only.

Recommendation-only run (prints the rendered compass, sends nothing):

```bash
python3 shared-goals/scripts/daily-compass.py

# Send one Telegram message per area plus a status message (cron and `make compass-run`):
python3 shared-goals/scripts/daily-compass.py --send

Update Compass.md Shared Goals section from platform:

python3 shared-goals/scripts/daily-shared-goals-status.py --update-compass
```

## Daily Compass troubleshooting

Debug a bad or degraded Daily Compass run from the trace log, not from the sent message:

1. Read the newest `logs/<stamp>.log` in this skill directory (one per run; `<stamp>.<area>.log` for per-area detail). The sent Telegram message is a render — it hides what failed.
2. The log is split into named phases: `Phase 1: boundary scripts`, `Phase 2: signal prompts`, `Phase 3: signal responses`, then render/delivery. Match the symptom to a phase: raw boundary JSON in the output means Phase 3 failed entirely; `[ERR:hermes_unavailable]` is the sentinel value `run_hermes_raw()` returns on any LLM-call exception — grep the log for `auxiliary call failed` to see the real error.
3. Do not trust cron status: a run where every signal fails can still report `ok`. Check `Phase 3 area signal complete: processed=X, failed=Y` in the log before concluding health.
4. The signal pipeline resolves its LLM endpoint from the Hermes config (`scripts/compass/llm.py`, `resolve_endpoint`). After any `hermes update` or config-schema migration, grep that resolver against the current `~/.hermes/config.yaml` provider section BEFORE assuming the pipeline is broken elsewhere — a schema rename makes every call fail instantly with `elapsed=0.0s`, which distinguishes config mismatch from a network/model problem (real network failures have elapsed > 0 and retries).
