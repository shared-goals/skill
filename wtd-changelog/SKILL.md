# Заметки Шага про изменения в Тексте

## When to Use

- «Сделай дайджест», «заметки про изменения в Тексте», «пост в канал», «что изменилось с прошлой публикации».
- НЕ для: вычитки русского (это `make grammar` в whattodo), разбора чужого контента против Текста (`wtd-content-analyze`), физической отправки файла в Telegram (`telegram-delivery`), пересборки книг (`wtd-books`).

Класс задачи: написать для публичного канала автора вторую часть поста — заметки об изменениях в Тексте, с моим авторством. Первую часть пишет автор, и она не моя.

## Пост состоит из двух частей, и авторы разные

| Часть | Автор | Что это |
|---|---|---|
| 1. Вступление | автор | место, событие, мысль, жизнь. Идея поста |
| 2. Заметки об изменениях в Тексте | я, подписаны мной | 5–7 пунктов со ссылками на разделы |

Подводка к моей части — одна строка, как в опубликованных постах: «Далее заметки Шага про изменения в Тексте с <даты>:». Вступление не писать никогда, даже как черновик: в черновике на его месте стоит `[вступление автора]`.

## Формат пункта

```
- В главе об [Общих целях](https://text.sharedgoals.ru/p2-180-sharedgoals/#agent_harness) — большой
  новый блок про harness для ИИ-агентов: как выбирать модели, принципы доверенного помощника.
```

- Один пункт = один смысловой сдвиг. Не файл, не раздел, не строка диффа.
- Глагол о смене смысла: «появился блок», «превратилась из заготовки в черновик», «переименован и существенно расширен».
- Ссылка — на **якорь раздела**, а не на главу целиком: читатель должен попасть в то место, о котором речь.
- Номеров строк, размеров диффа и «в файле X изменено Y строк» в посте не бывает.
- Telegram-markdown: жирный, `||спойлер||`, ссылки; никаких таблиц и заголовков `#`.

## Входа-таргета нет — и не надо

`make changelog` удалён вместе с промптом: дайджест не запускается одной командой, его пишу я в разговоре с автором. Механику собираю сам, в терминале:

```sh
cd "$WTD_DIR"  # путь к чекауту whattodo
# последний опубликованный пост — тегом; тега нет — от даты прошлого поста
BASE=$(git rev-list -n1 "$(git describe --tags --match 'post/*' --abbrev=0 2>/dev/null)" 2>/dev/null) \
  || BASE=$(git log --oneline --after="<дата>" --reverse -- 'text/*.md' | head -1 | cut -d' ' -f1)
git diff "$BASE"..HEAD --name-only -- ':(glob)text/p1-*.md' ':(glob)text/p2-*.md' 'text/index.md'
git diff "$BASE"..HEAD -- ':(glob)text/p1-*.md' ':(glob)text/p2-*.md' 'text/index.md'
env -u VIRTUAL_ENV uv run --project ../text-forge python \
    ../text-forge/scripts/books-changed.py --root "$PWD" --since "$BASE" --md build/books-changed.md
```

Книжный список — материал для части автора, не для моей: он показывает «что прочитано с даты», я из него беру только названия, если они объясняют правку в главе.

Объём диапазона мерить сразу — он определяет стратегию: `git diff "$BASE"..HEAD -- <главы> | grep -c '^+[^+]'` и число файлов. Три месяца правок — это сотни строк и два десятка глав, одним прогоном модели такое даёт перечень, а не дайджест.

## Порядок

1. **Якорь.** «С прошлой публикации» — состояние, а не ref: пост мог что-то не упомянуть, и следующий не должен повторять сказанное. Тег `post/YYYY-MM-DD` **на коммите публикации** решает это без новых файлов и без догадок: `git tag -a post/2026-08-18 <sha>` сразу после поста, диапазон — `$BASE..HEAD` (сам коммит публикации исключён, он уже рассказан). Тега нет — дата прошлого поста → первый коммит после неё (`git log --oneline --after=… --reverse … | head -1`); это приближение: если тот коммит уже был в посте, оставь его как базу; чтобы включить его в дайджест, возьми его родителя. Ставя тег, ты снимаешь вопрос навсегда.
2. **Карта разделов.** Не читать дифф подряд: `scripts/section_map.py --base <ref>` печатает по каждому файлу разделы, куда легли добавленные строки, и их объём. Дальше открывать только то, что по объёму и по названию похоже на смысловой сдвиг. Вопрос «раздел новый или выросший» карта решает **по заголовку** (`--new-headings`), а переименование заголовок меняет — поэтому переименованный раздел карта показывает как новый. Проверять это **`section-diff.py` из text-forge** — раздел идентифицируется якорем, поэтому переименование видно как переименование (см. Грабли):

```sh
env -u VIRTUAL_ENV uv run --project ../text-forge python \
    ../text-forge/scripts/section-diff.py --root . --base "$BASE" --head HEAD \
    --file text/p2-110-system.md
```
3. **Гипотезы из памяти.** `hindsight_recall` за период даёт события, которых в диффе не видно: переезд на другую платформу, новая практика, прочитанная книга, разговор, породивший раздел.
4. **Память предлагает, текст подтверждает.** Пункт попадает в заметки только если изменение есть в файле. Иначе в канале окажется рассказ о нашей переписке, а не об изменениях Текста. Обратное тоже верно: память даёт имя смыслу, дифф даёт право его назвать.
5. **Отбор 5–7.** Меняет мысль Текста — берём. Типографика, перелинковка, черновые перестановки абзацев, чистка мёртвых ссылок — не берём. Если кандидатов больше, лучше меньше пунктов с точным смыслом.
6. **Проверка ссылок — в два шага, иначе проверка врёт.** `{#anchor}` в файле — необходимое условие; `curl -o /dev/null -w '%{http_code}'` даёт 200 на **любой** якорь, потому что mkdocs отдаёт страницу целиком, а якорь ищет браузер по `id=`. Значит проверять так: `curl -s "$page" | grep -q "id=\"$anchor\""` — и только потом считать ссылку живой. Битая ссылка в канале хуже отсутствия пункта.
7. **Черновик.** Часть 1 — `[вступление автора]`, часть 2 — подводка и пункты. Отдать автору на правку.

## Грабли

- **Книги — в его части.** В опубликованных постах «Прочитал книжку «Pro Git»» и подобное стоит во вступлении, а заметки — только про главы. Список изменённых книг (сотни записей за месяцы) — материал для него, не для меня; иначе дайджест превращается в список прочитанного.
- **Не публиковать без прямого приказа.** Пост в канал — внешнее действие: черновик, правка, публикация по слову.
- **Не выдумывать событий из памяти.** Уверенное воспоминание без следа в файле — не факт о Тексте.
- **Книжные страницы и `p3-references.md` в дифф не тащить.** Это цитаты третьих лиц и
  генерируемый вывод: на реальном диффе они дают больше половины строк. Поэтому скоуп в
  командах выше назван семействами (`p1-*`, `p2-*`, `index`): плейн-glob `text/*.md`
  перекрывает `/` и притянет `text/books/**`.
- **«С начала июля» ≠ дата поста.** Относительная формулировка в подводке должна соответствовать проверенному диапазону, иначе заметки и подводка разъезжаются.
- **`make changelog` больше нет.** Не искать таргет и не восстанавливать: промпт `text_forge/prompts/changelog.md` удалён, вход собирается командами выше.
- **Раздел существовал до диапазона — и это нормально.** Самая частая ошибка: увидеть 40 добавленных строк в разделе и рассказать в посте его содержание целиком. Читатель уже это читал в прошлый раз. Пункт про старый раздел обязан звучать как «было так → стало так», иначе его нет.
- **Якорь — идентичность раздела, заголовок — нет.** При переименовании якорь сохраняется, поэтому сравнение по паре «заголовок+якорь» объявляет переименованный раздел новым, и весь его текст выглядит добавленным. `section-diff.py` (text-forge) сравнивает по якорю и отдельно печатает переименования.
- **Переписанный раздел — не «новый раздел».** Признак переписывания — сопоставимые `+N/-M`. Если в главе 20 разделов и все они тронуты, это «глава переписана», а не «20 новых разделов»; в посте такая глава занимает один пункт, и в нём — только появившиеся утверждения.
- **Новый раздел бывает переносом.** Глава переписывается и блок переезжает: у соседа `+4/-22`, а рядом «новый раздел» с тем же текстом. Признак: удалённые строки одного раздела и добавленные другого говорят об одном и том же. Перед словом «появился» искать удалённый текст по всему файлу (`git show $BASE:FILE | grep`) — переезд в посте не новость, а реорганизация.
- **База может измениться.** Во время подготовки дайджеста автор может опубликовать правки из другого чекаута. Перед показом черновика — `git pull`, затем перепроверить якоря и дельты на свежем HEAD: правка может убрать `{#anchor}` вместе с заголовком, и ссылка из готового пункта станет битой.
- **Один и тот же пункт дважды.** Событие часто оставляет след в двух главах; в посте это один пункт со ссылкой на главный раздел.

## Проверка перед показом

0. Каждый пункт выдерживает вопрос «что здесь сказано такого, чего в Тексте не было до диапазона?» — с конкретной цитатой из вывода `section-diff.py` (text-forge). Пункт, который пересказывает уже написанное, вычёркивается до показа.
0.1. Характерные слова каждого пункта (метафоры, термины, обороты) находятся в файле на HEAD: `grep -c "формулировка" text/<глава>.md` ≠ 0. Ноль — пункт цитирует версию, которой уже нет: дифф показывает, что автор писал по пути, а HEAD — что осталось; метафору из `+`-строки он мог вычеркнуть следующей правкой.
0.2. Устойчивость процедуры: после стилевой правки автора (вычитка по отчёту `make grammar`, перенос ссылок на `books/*.md`) повторный прогон обязан дать ТОТ ЖЕ набор пунктов. Набор изменился — фильтр пропускает стиль, а не смысл, и «новый» пункт надо вычёркивать, а не показывать.
1. Каждый пункт: ссылка открывается, якорь ведёт в изменённый раздел. Проверено на свежем HEAD после `git pull`, а не на чекауте часовой давности.
2. Вступление — заглушка, а не написанный мной текст.
3. В заметках нет книг, номеров строк и пересказа диффа.
4. Подводка называет тот период, который реально проверен.
5. Ни один пункт не описывает перенос материала как появление.

## Поддерживающие файлы

- `scripts/section_map.py` — `--base <ref>`: разделы с числом добавленных строк; `--new-headings`: появившиеся разделы. Без аргументов — wtd-скоуп, книги и `p3` не трогает.
- `section-diff.py` живёт **в text-forge** (`scripts/section-diff.py`, логика в `text_forge/section_diff.py`, тесты в `tests/test_section_diff.py`): сравнить ревизии markdown по разделам — задача не про этот канал, а про любой текст. Осталось у скилла только решение «что из дельты достойно поста».
