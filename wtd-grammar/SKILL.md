# Разбор русской прозы на ошибки

## When to Use

- «Проверь грамматику», «вычитай главу», «найди ошибки в Тексте», «разбери дифф» — любой вычит русского текста.
- Правка или разбор `make grammar` в whattodo и промпта вычитки — он живёт в text-forge: `text_forge/prompts/grammar.md` (package data), сборка job-файла — `scripts/job.py`.
- Нужно объяснить правило русского языка со ссылкой на orfogrammka.ru.
- НЕ для: подбора слов и стиля (это `russian-expressive-lexicon`), для пересборки `text/books` (это `wtd-books`).

Класс задачи: вычитать русский текст (главы WTD, статьи, заметки), найти ошибки, объяснить каждую через правило с настоящей ссылкой на orfogrammka.ru. Автор правит сам — задача не «исправить», а «показать ошибку, правило и как чинить».

## Незыблемое

- **Текст не править.** Находки — в отчёт: `build/grammar-report.md` для прогона через `make grammar`, `build/grammar-review.md` для ручного разбора. Отдать через `MEDIA:/абсолютный/путь`. Правку в репозитории делать только по прямому приказу.
- **Каждая находка = `файл:строка` + цитата + тип + объяснение + ссылка на правило + предложенная правка.** Без адреса находка бесполезна: строку придётся искать вручную.
- **Проверяем только авторский текст:** `text/p1-*.md`, `text/p2-*.md`, `text/index.md`. Вне вычитки: `text/books/*` (чужие цитаты) и `text/p3-references.md` (генерируется из книг и рецензий).
- **Чужое не трогать:** блоки `/// quote`, эпиграфы, цитаты внутри глав. Там могут быть настоящие ошибки — они не наши.
- **Авторские заглавные** (Должен, Люблю, Вера, Свобода, Призвание) — не ошибки, это его система понятий.
- **Точность важнее объёма.** Сомнительное — либо помечать «спорное, норма допускает и так», либо выбрасывать. Выдуманная ошибка стоит дороже пропущенной: по ней будут «учить правило», которого нет.
- **Ссылку на правило не придумывать никогда.** Каталог доступен (см. `references/orfogrammka-rule-catalog.md`) — брать URL оттуда. Правила под случай нет → писать «отдельного правила нет, это смысл/стиль».

## Классификация находок

Делите находки на три вида — от вида зависит, что писать в отчёте:

| Вид | Признак | Что предлагать |
|---|---|---|
| **Опечатка** | окончание не той формы, латинская буква в русском слове, лишний пробел, «эколюционной» | одну правку без разбора: правило формальное, смысл не страдал |
| **Настоящая ошибка** | нарушено правило: падеж после предлога, тире вместо запятой, «в течении», «ни/не» | правило + URL + правку; это то, что он учит |
| **Ошибка + тяжёлая фраза** | правило нарушено, и само предложение перегружено: два-три придаточных, вставка в обороте, с первого раза не читается | сначала «почему фраза тяжёлая», потом переписанный вариант; запятая проблему не решает |

Тяжёлую фразу не «чинят пунктуацией»: если после расстановки запятых её всё равно надо перечитывать — предлагать разбивку на два предложения.

## Порядок

### 1. Сузить дифф до авторского текста

Основной путь — `grammar-diff` из text-forge (модуль `text_forge/grammar.py` + CLI). Он сохраняет номера строк, отбрасывает перелинковку, строки внутри `/// quote`, markdown-структуру и печатает счётчики отброшенного:

```bash
cd "$WTD_DIR"  # путь к чекауту whattodo
# дифф от коммита (включительно) — обычная форма
env -u VIRTUAL_ENV uv run --project ../text-forge python \
  ../text-forge/scripts/grammar-diff.py --root "$PWD" --since <ref> \
  --scope wtd --typo --md build/grammar-input.md --json build/grammar-input.json

# один файл целиком, без диффа — для главы, которую давно не трогали
… --root "$PWD" --only text/p2-110-system.md --typo \
  --md build/grammar-input.md --json build/grammar-input.json
```

`--only FILE` читает файл целиком (все строки считаются добавленными, фильтры те же, `link_only=0`) и несовместим с `--since`. «Весь текст» = цикл по главам: `for f in text/p*.md text/index.md; do make grammar $f; done` — один прогон на ~40 минут, а отчёт каждый раз перезаписывается в `build/grammar-report.md`, поэтому копировать его надо после каждой главы.

`--scope wtd` = `text/p1-*.md` + `text/p2-*.md` + `text/index.md`; `--scope all` захватывает `text/**/*.md`, включая книжки. Без `--since` берётся рабочее дерево против HEAD. Коды выхода: `0` — ок, `1` — ref не разрешился, `2` — добавленных строк нет.

Результат — `build/grammar-input.md` со строками вида `text/p2-110-system.md:31 | …`: этот файл и идёт в вычитку. Если инструмента под рукой нет, справка в `scripts/`:

```bash
python3 <skill>/scripts/added_lines.py <base-ref> -- text/p1-*.md text/p2-*.md text/index.md
python3 <skill>/scripts/scan_typography.py build/added_lines.json
```

Даёт `build/added_lines.json`: `{файл: [[номер_строки_постинга, текст], ...]}`.

### 2. Машинный проход по типографике

Двойные пробелы, пробел перед знаком, латиница внутри русских слов. Дешевле, чем глазами, и модель такое часто «не видит».

### 3. Читать прозу по классам

Печатать добавленные строки пачками (5–10 файлов на вызов) и разбирать по классам: согласование и падеж → пунктуация → не/ни и производные предлоги → обрывы фразы → тяжёлые фразы → типографика. Смысловые поломки ищутся на чтении, типографика — скриптом.

### 4. Проверить каждую находку до отчёта

Перечитать фразу целиком и спросить: «а нет ли нормы, которая это разрешает?». Реальные снятия: «Докопаться до сути и найти решение требует большого труда» — при подлежащем-инфинитиве ед. ч. законно, не ошибка; «И та и другая характеристика превосходят» — спорное, выбрасывать. Отчёт с ложной находкой учит неправильно.

Правишь промпт — прогони по нему эталонные случаи (`text-forge/tests/fixtures/grammar/cases.md`): там 38 фраз в обе стороны, включая те, что помечать НЕЛЬЗЯ (подлежащее-инфинитив, блоки `/// quote`, авторские заглавные, «в течении реки»). Ложное срабатывание на них — блокер правки.

### 5. Взять правило из каталога

Проверенные страницы по классам ошибок и как достать остальное — `references/orfogrammka-rule-catalog.md`. URL писать раскодированным (кириллицей): так он читаем и в markdown, и в браузере.

### 6. Отчёт

Структура, которая работает:

1. Что проверялось: base-ref, сколько строк, что исключено и почему.
2. Как устроена текущая проверка (если речь о `make grammar`) — дефекты с номерами строк Makefile.
3. Ошибки по классам, severity внутри класса, каждая с `файл:строка`, цитатой, правилом и URL.
4. «Что здесь важнее отдельных ошибок» — повторяющиеся классы (привычки) с числом повторов: ради этого он и читает.
5. Типографика таблицей (её чинят машинно).
6. Варианты улучшения процесса с плюсами/минусами и рекомендованным порядком. Действия не начинать — ждать решения.

### 7. Проверить отчёт механически, до показа

Отчёт пишет модель, находок десятки, и глазами проверяются две-три. Прогони
чекер адресов: он сверяет каждую пару `файл:строка` с диском, а цитату — со
строкой по этому адресу.

```bash
python3 <skill>/scripts/check_report_addresses.py build/grammar-report.md "$PWD"
```

`ok=56 mismatch=0 no_address=0` — можно отдавать. Любой `MISMATCH`/`NO FILE` —
находка битая: либо адрес съехал (правился текст после прогона), либо цитата
сочинена. Не отдавать отчёт, пока расхождения не объяснены: адрес — это то,
ради чего отчёт существует.

Отдельно проверь ссылки на правила: все URL в отчёте должны встречаться в
`references/orfogrammka-rule-catalog.md`. Один `grep -o` по отчёту и сверка со
списком — секунда, а придуманная ссылка учит несуществующему правилу.

## Грабли

- **`text/*.md` в git захватывает `text/books/*.md`.** Звёздочка в pathspec перекрывает `/`, поэтому «авторский текст» по умолчанию тянет сотни цитат третьих лиц. Перечислять файлы явно.
- **Генерируемые страницы в скоуп не брать.** `text/p3-references.md` рендерится из `text/books` + рецензий (`text_forge/wtd_books_p3.py`): на реальном диффе это больше половины сырых строк, и вычитывать там нечего — правится генератор, а не вывод. Тот же класс — `text/books/*`. Скоуп называть семействами явно (`p1-*`, `p2-*`, `index`), а не `text/p*.md`: звёздочка в `p*` тихо захватит и `p3`.
- **Кириллица/латиница внутри текста ссылки теряется фильтром «токен содержит `](`».** `[Cмерти](p1-010-happiness.md#x)` пропускался целиком. Правильно: вырезать цели ссылок (`\]\([^)]*\)` → `]`) до токенизации, тогда проверяется только текст ссылки, а URL остаётся шумом.
- **Счётчики не должны терять строки.** `kept + Σdropped` обязано равняться числу добавленных строк, которое git показывает для того же pathspec (`git diff --numstat`); расхождение — тихий баг фильтра, а не «нет изменений».
- **Утверждение о путях проверять числом, а не на слово.** «Этот глоб книжек не захватывает» звучит правдоподобно и бывает неверным: `git diff --name-only <base>..HEAD -- 'text/*.md' | grep -c 'text/books/'` даёт ответ за секунду. То же для числа строк: сначала пересчитать самому, потом принимать объяснение.
- **`git diff | grep '^+'` убивает номера строк.** Заголовки ханков `@@ -a,b +c,d @@` отбрасываются вместе с ними. Парсить `git diff -U0` и считать строки от `+c`, иначе в отчёте будет «Location: not available».
- **Шум перелинковки вытесняет прозу.** Замена URL цитат на локальные `books/...#quote_N` — это большинство добавленных строк в диффе. Отбрасывать строки, где изменилась только ссылка.
- **Двойной пробел в конце строки — не ошибка.** В стихах внутри `/// quote` это markdown-перенос. Ошибка — двойной пробел внутри фразы.
- **Латиница внутри кириллического слова** (`Eдиная`, `cвязывать`, `Cмерти`) не ловится проверкой орфографии, но ломает поиск и индексацию. Отдельный пункт в типографике.
- **Хабы правил пустые.** Например `/грамматика/согласование-сказуемого-с-подлежащим` — только оглавление подстраниц. Ссылаться на подстраницу, а если её нет — честно писать, что это раздел, а не правило.
- **`opencode` устарел.** Harness для кодинга и для проверки — `pi` (pi.dev). Встретил `opencode` в Makefile или промпте — это долг, а не образец.
- **`make grammar` — штатный вход, и он уже собран правильно.** Три формы, и только они (контракт интерфейса):
  - `make grammar` — рабочее дерево;
  - `make grammar <sha>` — с этого коммита **включительно** (`<sha>^..HEAD`); у корневого коммита родителя нет → внятная ошибка, а не тихий пустой прогон;
  - `make grammar <file.md>` — один файл целиком, без диффа.
  Позиционный аргумент, который является существующим путём, считается файлом, иначе — ref. Режима «весь текст» **нет и не будет**: 8 188 строк корпуса при ~40 минутах на 337 строк — это ночь, и одним промптом модель смотрит поверхностно. «Весь текст» = цикл по главам.
  `GRAMMAR_SINCE=` как переменная командной строки удалена вместе с ловушкой: cmdline-присваивание перебивало внутреннее, и таргет отчитывался «нечего проверять», ничего не проверив. `GRAMMAR_RUNNER=stub` собирает job-файл без вызова модели — дешёвая проверка, что рецепт и промпт склеились (`wc -l`, `grep -c 'text/books/'` = 0).
  Промпт и склейку держать в одном репозитории с инструментом (text-forge: `text_forge/prompts/grammar.md`, `scripts/job.py`): формат входа и ожидания промпта — один контракт, а раздельно они уже разъезжались. Общая механика таких target'ов — в скилле `pi-coding-agent`, файл `make-prompt-jobs.md`.
- **Вывод инструмента — English в stderr, отчёт — русский в файле.** Строки `grammar-diff`, `job.py`, `pi-run.py` печатаются через `text_forge/console.py` (rich) в **stderr**: stdout остаётся пустым, чтобы косметика не попадала в пайпы и `$(...)`. В non-TTY rich сам отдаёт плоский текст без ANSI — отдельной ветки для cron нет. Прогресс прогона модели рисует `scripts/pi-run.py` из `pi --mode json` (события `message_update`/`tool_execution_*`): живая строка в TTY, молчание в фоне, финальный ответ модели — в конце. Промпт поэтому требует ответ свободным текстом без markdown: терминал разметку не рендерит.
- **Гейт перед публикацией — вопрос, не блокировка.** `make publish` спрашивает «Проверить грамматику? [y/N]»; при `y` прогон, отчёт и **стоп до любой записи в git**: публиковать с известными находками — осознанный шаг, а не дефолт. Обязательным гейтом вычитку не делать: она стоит десятки минут и зависит от модели.
- **Не путать отчёт вычитки с отчётом прошлого прогона.** `build/grammar-report.md` перезаписывается только когда модель дошла до записи; старый файл живёт после неудачного прогона и выглядит как свежий. Перед чтением сверь шапку отчёта (base-ref и число строк) с входом, который только что собрался.
- **Сборочная машинерия живёт в text-forge, не в whattodo.** `whattodo` — это текст + `mkdocs.yml` + тонкий Makefile; скрипты, тесты и uv-окружение — `text-forge` (`scripts/`, `tests/`, `text_forge/`). Новый инструмент вычитки кладётся туда как модуль + CLI, а Makefile whattodo вызывает его через `env -u VIRTUAL_ENV uv run --project $(TEXT_FORGE_DIR) python $(TEXT_FORGE_DIR)/scripts/…` — **с окружением text-forge**, потому что зависимости инструмента живут с инструментом (`rich` для вывода), а не в env контентного репозитория. Забыть `--project` = `ModuleNotFoundError` на первом же импорте. Иначе появятся две расходящиеся реализации и тесты без дома.
- **Отчёт цитирует текст без целей ссылок.** Модель по контракту печатает цитату «как читается» — `](books/x.md#quote_3)` из неё выпадает, а в файле остаётся. Наивное сравнение строк объявляет расхождением почти каждую находку; сравнивать надо после нормализации (`](...)` → `]`, снять `*`, `_`, backticks, многоточие = граница фрагмента). Это делает `scripts/check_report_addresses.py`, не переписывай его по-своему на ходу.
- **Для вычитки не нужен MCP:** ссылки на правила берутся из каталога.

## Поддерживающие файлы

- `references/orfogrammka-rule-catalog.md` — навигация по каталогу правил, проверенные URL по классам, рецепт выгрузки.
- `scripts/scrape_rules.py` — выгрузка полного индекса правил (679 записей) в JSON.
- `scripts/check_report_addresses.py` — сверка отчёта с диском: адреса `файл:строка` и цитаты (с нормализацией ссылок).
- `scripts/added_lines.py` — дифф → `{файл: [[строка, текст]]}` (справка до переезда в text-forge).
- `scripts/scan_typography.py` — машинный проход по типографике.
